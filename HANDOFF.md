## Failed Approaches (Don't Repeat These)

- **Assumed system-market listings had no fixed expiry**, based on
  observing listing *age* (`dt` field) ranging 2h–28h with no obvious
  cap. Wrong — the real expiry field is `exs` (seconds remaining), which
  is present on every system listing regardless of bid state; age and
  time-to-expiry are unrelated. Caught when the user reported a live
  contradiction (app showed "4 min left", dashboard said "no time limit").
  Fix: read `exs` directly instead of inferring from listing age.
- **Assumed GitHub Pages could be made access-restricted for a private
  personal-account repo** (Free or Pro tier). Verified live against
  current GitHub docs: restricted-visibility Pages requires the repo to
  be owned by an **organization** on **GitHub Enterprise Cloud** — not
  available for personal accounts at any tier. This is why the plan
  pivoted to "repo goes public + Firebase Auth gates the live data
  instead of the hosting layer."
- **User's initial idea: gate the dashboard with actual Kickbase-account
  login** (so anyone logging in with their own Kickbase credentials sees
  their own league data). Rejected — would mean collecting third-party
  Kickbase passwords through an unofficial reverse-engineered API proxy.
  Replaced with Firebase Auth (single user, matches the existing
  f1-tipping-game project's proven pattern).
- **Considered Cloud SQL / Turso as a "just keep SQL" alternative to
  Firestore.** Cloud SQL has no real always-on free tier (conflicts with
  the user's stated 0€-hobby-project preference). Turso would keep SQL
  syntax but has no native "Firebase Auth checks on read" mechanism —
  would require hand-building a backend API just to enforce access,
  which is exactly the complexity Firestore Security Rules avoid.
- **"Stammspieler" almost got implemented using `status_code` 1/2.** The
  user's own wording matched that, but the project's established
  convention (`MDs/codes.md`) defines status_code 1/2 as
  injured/knocked — the opposite of "regular starter." Caught via
  `AskUserQuestion` before implementing; correct definition is
  `starting_rank` 1 or 2 (Startelf-Rang).
- **`get_manager_squad()` (opponent squads) does not return
  `starting_rank`/`prob` per player** — confirmed live. Needed a separate
  lookup built from `player_valuation.fetch_all_players()` instead
  (already fetched for other reasons, reused rather than re-fetched).

## Key Decisions

| Decision | Rationale |
|----------|-----------|
| Firestore over Cloud SQL/Turso | Native Firebase Auth + Security Rules integration; genuinely free; current SQL usage has no JOINs anyway (see Failed Approaches) |
| New, separate Firebase project ("KickbaseAgent") | Clean separation from the unrelated f1-tipping-game project, even though it also uses Firebase Auth |
| SQLite stays, Firestore is additive | No cutover risk; existing ML training / budget estimation logic reads from Kickbase's API directly anyway, not from our own DB, so there's no urgency to migrate it |
| Repo goes public | User judges the risk as low ("nobody in my league will care"); tradeoff is that `MDs/*.md` (strategy notes) and `data/wunschkader.json` (target list) become visible to anyone who finds the repo — accepted knowingly |
| Firebase Auth, not Kickbase-account login | Avoids collecting third-party Kickbase passwords via an unofficial API |
| 2-hour refresh cadence | Matches Kickbase's own cadence for rotating system-market offers; well within GitHub Actions free quota |
| `FIRESTORE_ENABLED` feature flag | Local dev/sandbox runs without Firebase credentials must keep working unchanged |

match** (same row-dict inputs, just a different persistence backend):

```python

def replace_own_squad(conn, fetched_at: str, players: list[dict]) -> None: ...
def replace_market_listings(conn, fetched_at: str, listings: list[dict]) -> None: ...
def replace_league_ranking(conn, fetched_at: str, rows: list[dict]) -> None: ...

def upsert_season_context(conn, fetched_at: str, context: dict) -> None: ...
def replace_manager_budgets(conn, fetched_at: str, rows: list[dict]) -> None: ...
```
Tables (→ target Firestore collections, same names): `own_squad`,
`market_listings`, `league_ranking`, `own_budget_history`,
`season_context`, `manager_budgets`. Doc ID convention agreed in the spec:
`{fetched_at}_{player_id}` or `{fetched_at}_{user_id}` (plain `{fetched_at}`
where there's only one row per day, e.g. `season_context`).

**Feature-flag pattern to replicate** (matches existing resilience style,
e.g. `_apply_market_value_history` in `fetcher.py`):
```python
if os.environ.get("FIRESTORE_ENABLED"):
    try:
        firestore_db.replace_own_squad(fs_client, fetched_at, own_squad_rows)
    except Exception as exc:  # a Firestore outage must never break the pipeline
        print(f"Warnung: Firestore-Schreibzugriff fehlgeschlagen: {exc}", file=sys.stderr)
```

## Edge Cases & Error Handling

- Firestore write failure must never break the existing pipeline (Discord
  report / dashboard export must still complete) — wrap in try/except
  with a stderr warning, exactly like every other resilience point in
  this codebase (`_apply_market_value_history`, achievement bonus fetch,
  etc.).
- Running without `FIRESTORE_ENABLED` set (the default in this sandbox
  today) must remain 100% unaffected — no import-time Firebase client
  initialization, no credential lookup unless the flag is on.
- Batch writes exceeding Firestore's 500-operations-per-batch limit:
  none of the current data volumes (own squad ~14-18 players, market
  ~50-60 listings, ranking = league size ~8) will ever hit this, but keep
  the batching code correct anyway rather than assuming it never matters.
