# Grafische Tab-Indikatoren — Naming/Ablage-Kontrakt + Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Jeder der 8 App-Tabs bekommt ein eigenes Icon in Desktop-Nav + Mobile-Burger-Menü, statt reinem Text-Label.

**Architecture:** Folgt 1:1 dem bestehenden Icon-Muster dieses Projekts (`frontend/public/icons-src/` als Rohdatei-Staging, `frontend/src/components/icons.tsx` als finale, in React eingebettete `currentColor`-SVGs — exakt wie bei den bereits vorhandenen Positions-/Status-Icons).

**Tech Stack:** Statische SVG-Dateien, React-Komponenten (kein neues Icon-Framework).

## Kontext — Design-Schritt läuft AUSSERHALB dieser Sandbox

User-Feedback (`feedback/current`, Item `89aaaa7d`, Backlog): "Grafische Indikatoren für die Tabs, hierfür müssen Ideen
gesammelt werden. Claude selber kann die auch erzeugen im Browser zB."

**Entschieden (Chat, 2026-08-03): der eigentliche visuelle Design-Schritt (Icon-Konzepte finden, SVGs erzeugen)
passiert NICHT in dieser Sandbox**, sondern manuell durch den User über Claude im Web-Browser (separater Chat, kein
Sandbox-Zugriff auf dieses Repo). Diese Sandbox liefert nur den Prompt dafür (siehe unten, außerhalb dieses
Plandokuments an den User ausgehändigt) sowie Naming-Konvention + Ablageort, damit die vom User zurückgebrachten
SVG-Dateien direkt maschinell weiterverarbeitet werden können. **Nur die Implementation (Rohdatei → eingebundenes
React-Icon → Verdrahtung in Nav/Burger-Menü) passiert hier.**

## Naming- und Ablage-Kontrakt

Der User legt die vom Claude-Web-Chat gelieferten SVGs unter diesem exakten Pfad/Namen ab, **bevor** Task 1
ausgeführt werden kann:

| Tab-Key (`App.tsx` `TABS`) | Label | Datei |
|---|---|---|
| `team` | Eigenes Team | `frontend/public/icons-src/tab-team.svg` |
| `spekulation` | Spekulation | `frontend/public/icons-src/tab-spekulation.svg` |
| `wunschkader` | Wunschkader | `frontend/public/icons-src/tab-wunschkader.svg` |
| `transfermarkt` | Transfermarkt | `frontend/public/icons-src/tab-transfermarkt.svg` |
| `liga` | Ligaanalyse | `frontend/public/icons-src/tab-liga.svg` |
| `alle-spieler` | Alle Spieler | `frontend/public/icons-src/tab-alle-spieler.svg` |
| `ml-genauigkeit` | Modell-Tracking | `frontend/public/icons-src/tab-ml-genauigkeit.svg` |
| `feedback` | Bugs & Ideen | `frontend/public/icons-src/tab-feedback.svg` |

Namensschema `tab-<key>.svg` (kebab-case) folgt exakt dem bestehenden Muster in diesem Ordner
(`position-torwart.svg`, `status-fit.svg`, ...). `frontend/public/icons-src/` existiert bereits als Staging-Ordner
(committed inkl. Generator-Tooling, siehe `icons4.py`/`preview_icons4.py` dort) — Ablageort ist also kein neuer
Ordner, sondern Wiederverwendung des etablierten Musters.

**Erwartetes Format** (steht auch im Claude-Web-Prompt, hier zur Kontrolle beim Empfang der Dateien): `viewBox="0 0
24 24"`, ein einziges `fill="currentColor"` bzw. konsequent einfarbig (keine hartkodierten Farben/Gradients im
SVG — die Icons müssen sich wie alle bestehenden automatisch an Hell-/Dunkelmodus und Tab-Auswahlfarbe anpassen).

## Nicht-Ziele

- Keine Änderung an Tab-Reihenfolge, Tab-Labels oder Tab-Keys.
- Keine Status-Badges/Benachrichtigungs-Indikatoren auf den Tabs (z.B. "neue Angebote seit letztem Besuch") — reine
  Identitäts-Icons pro Tab, wie im Chat geklärt. Falls das eigentlich gemeint war, ist das ein separates, eigenes
  Feature.
- Kein Ersatz der bestehenden Text-Labels — Icon **zusätzlich** zum Label, nicht statt.

## Task 1: SVGs einbinden (blockiert, bis der User die 8 Dateien abgelegt hat)

**Voraussetzung:** Alle 8 Dateien aus der Tabelle oben liegen unter `frontend/public/icons-src/` vor. **Vor Start
dieses Tasks prüfen** (`ls frontend/public/icons-src/tab-*.svg` → müssen genau 8 sein) — falls nicht, Task nicht
beginnen, sondern beim User nachfragen, welche fehlen.

**Files:**
- Read: die 8 `frontend/public/icons-src/tab-*.svg`-Rohdateien
- Modify: `frontend/src/components/icons.tsx` (8 neue Icon-Komponenten ergänzen, gleiches Muster wie
  `IconPositionTorwart` etc.)
- Modify: `frontend/src/App.tsx` (neue `TAB_ICON`-Map + Verdrahtung in Desktop-`<nav>` UND `MobileTabMenu`)

**Interfaces:**
- Produziert: `TAB_ICON: Record<string, (props: SVGProps<SVGSVGElement>) => JSX.Element>` in `App.tsx`, keyed nach
  denselben Strings wie `TABS`/`ACTIVE_TABS` (`"team"`, `"spekulation"`, ...).

- [ ] **Step 1: Jede der 8 Rohdateien lesen und 1:1-Struktur-Check machen**

Für jede Datei: `viewBox="0 0 24 24"` vorhanden? Nur `fill="currentColor"` (kein `stroke`, keine anderen Farben,
kein `<style>`-Block, kein eingebettetes Rastergrafik-Element)? Falls eine Datei davon abweicht (z.B. andere
viewBox-Größe oder mehrfarbig), NICHT stillschweigend anpassen — dem User zurückmelden, welche Datei(en) vom
Kontrakt abweichen, bevor weitergemacht wird (könnte eine bewusste Design-Entscheidung des Web-Chats sein, die hier
nicht einfach überschrieben werden sollte).

- [ ] **Step 2: 8 neue Icon-Komponenten in `icons.tsx` ergänzen**

Für jeden Tab eine Funktion nach folgendem Muster (Inhalt der `<path>`/sonstigen Kind-Elemente 1:1 aus der
jeweiligen Rohdatei übernommen, nur die äußere `<svg>`-Struktur ggf. auf das exakte Format der bestehenden Icons
vereinheitlicht):

```tsx
export function IconTabTeam(props: SVGProps<SVGSVGElement>) {
  return (
    <svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" fill="currentColor" role="img" aria-label="Eigenes Team" {...props}>
      {/* Pfade 1:1 aus frontend/public/icons-src/tab-team.svg uebernommen */}
    </svg>
  );
}
```

Analog für `IconTabSpekulation`, `IconTabWunschkader`, `IconTabTransfermarkt`, `IconTabLiga`,
`IconTabAlleSpieler`, `IconTabMlGenauigkeit`, `IconTabFeedback` — `aria-label` jeweils das deutsche Tab-Label aus der
Tabelle oben (z.B. `"Modell-Tracking"`, `"Bugs & Ideen"`).

- [ ] **Step 3: `TAB_ICON`-Map in `App.tsx` ergänzen**

Direkt nach der bestehenden `TABS`-Konstante (Zeile ~34-43):

```ts
const TAB_ICON: Record<string, (props: import("react").SVGProps<SVGSVGElement>) => JSX.Element> = {
  team: IconTabTeam,
  spekulation: IconTabSpekulation,
  wunschkader: IconTabWunschkader,
  transfermarkt: IconTabTransfermarkt,
  liga: IconTabLiga,
  "alle-spieler": IconTabAlleSpieler,
  "ml-genauigkeit": IconTabMlGenauigkeit,
  feedback: IconTabFeedback,
};
```

Import ergänzen (Kopfbereich von `App.tsx`, neben den bestehenden Imports aus `./components/icons`):

```ts
import {
  IconTabTeam,
  IconTabSpekulation,
  IconTabWunschkader,
  IconTabTransfermarkt,
  IconTabLiga,
  IconTabAlleSpieler,
  IconTabMlGenauigkeit,
  IconTabFeedback,
} from "./components/icons";
```

- [ ] **Step 4: Desktop-`<nav>` verdrahten**

Im bestehenden `<nav>`-Rendering (dort wo `TABS.map(...)` das `tab.label` ausgibt, per `isActive`/`isSelected`
bereits vorhandene lokale Variablen), das Icon vor dem Label ergänzen:

```tsx
{TABS.map((tab) => {
  const isActive = ACTIVE_TABS.has(tab.key);
  const isSelected = tab.key === activeTab;
  const Icon = TAB_ICON[tab.key];
  return (
    // bestehendes <button>/<a> unveraendert, nur der Inhalt bekommt zusaetzlich:
    <>
      <Icon className="h-4 w-4" aria-hidden="true" />
      {tab.label}
    </>
  );
})}
```

(Exakte Einbettung an die bestehende JSX-Struktur der Nav-Buttons anpassen — `aria-hidden="true"` auf dem Icon,
weil `aria-label` schon auf dem sichtbaren Text-Label sitzt und sonst doppelt vorgelesen würde.)

- [ ] **Step 5: Mobile `MobileTabMenu` verdrahten**

Gleiches Prinzip in der `MobileTabMenu`-Komponente (`App.tsx`) — Icon vor jedem Menüpunkt-Label ergänzen, gleiche
`TAB_ICON[tab.key]`-Auflösung, gleiche `aria-hidden="true"`-Regel.
